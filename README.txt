CombatLog MAX 3.0
=================

CombatLog MAX 3.0 — звичайна робоча версія після тестової гілки 2.9.3–2.9.5 TEST.
Вона знову використовує стандартний localhost та робочу папку data.

ВАЖЛИВО ПЕРЕД ПЕРШИМ ЗАПУСКОМ
-----------------------------
1. Штатно закрий попередню робочу CombatLog 2.9.2.
2. Не запускай 2.9.2 і 3.0 паралельно: обидві робочі версії використовують 127.0.0.1:18765 та data\combatlog.json.
3. При першому відкритті старої schema 18/19 версія 3.0 ДО міграції автоматично створює сирий backup у data\backups\pre_migration_schema...json.
4. Не видаляй цей backup, доки не перевіриш роботу 3.0 на своїй базі.
5. Після переходу база зберігається у schema 20. Стара 2.9.2 її не прочитає; для відкату треба повернути pre-migration backup.

ГОЛОВНА АРХІТЕКТУРА
-------------------
- Події — головний read-only хронологічний екран. Дані тут не дублюються.
- Вильоти — робочий модуль БпЛА.
- Місії — робочий модуль наземних місій; НРК реалізовано, Автомобіль/Група підготовлені як data-driven типи.
- Звіти — окремий модуль звітності.
- БпЛА/засоби, довідники, шаблони інших модулів та пресети часу знаходяться у ⚙ Налаштування.

БПЛА / ЗАСОБИ
--------------
Ієрархія: клас -> засіб -> модель -> дозволені дії.
Модель — дані, а не окремий тип засобу і не носій бізнес-логіки.

Для кожного засобу доступний єдиний каталог полів. Оператор сам задає:
- чи використовується поле;
- основне воно чи додаткове.

Для всіх БпЛА існує рівно три типи довідок:
- Ураження;
- Втрата борту;
- Мінування.

Кожен конкретний засіб має власні шаблони потрібних йому типів. Немає окремої runtime-логіки для FPV-оптоволокна, MATRICE, MAVIC, VAMPIRE тощо.

КЕРОВАНИЙ ВВІД ВИЛЬОТУ
-----------------------
Ручний ввід і результат парсингу використовують один редактор.
Після вибору позиції програма може запропонувати:
- наступний № вильоту для цієї дати + позиції;
- останній екіпаж та пілота цієї позиції;
- останній дозволений засіб або єдиний дозволений засіб позиції.

Це лише підказки: кожне автопідставлене значення можна змінити.
Форма веде послідовно: Виліт -> Епізод -> Дія -> Результат -> деталізація -> перевірка -> збереження.
Кнопки додавання БК, ураження/втрат та нового епізоду є помітними діями форми.

ПОДІЇ
-----
Події проєктують хронологічні факти з вихідних модулів. Один БпЛА-виліт може містити кілька епізодів, тому кількість Подій може бути більшою за кількість Вильотів.

Статистика Подій показує:
- Подій;
- Вильотів — унікальні вихідні вильоти, не кількість епізодів;
- Місій розпочато;
- Місій завершено;
- На виконанні;
- Втрат;
- Позиційних подій.

Блок «ЗАРАЗ НА ВИКОНАННІ» незалежно від історичного фільтра показує незакриті місії.

МІСІЇ НРК
----------
Одна строка = одна місія від початку до результату, плюс за потреби подальше уточнення/евакуація.
НРК вводиться вручну; парсер довідок БпЛА до нього не застосовується.
Обліку фізичних бортів немає. S/N та Starlink-поля виникають тільки у випадку втрати/знищення, якщо вони потрібні довідці.

Початкова точка і маршрут у schema 20 універсальні:
- існуюча позиція CombatLog; або
- довільне місце.

Типово місія стартує з ВП НРК, але це не обмеження. Можна вибрати іншу наявну позицію або написати довільне місце.

Правило регістру:
- ІМЕНОВАНІ позиції CombatLog канонічно зберігаються/показуються великими літерами: ВП НРК «ГВИНТИК», ЗПМ «ПРАДА»;
- ДОВІЛЬНІ місця зберігаються саме так, як введені: «позиції, що облаштовується», «район завантаження» тощо.

Позивні пілотів, екіпажі/групи, іменовані позиції та населені пункти залишаються у верхньому регістрі згідно з політикою відповідного каталогу.

BACKUP / IMPORT
---------------
- Робоча база: data\combatlog.json.
- Автоматичні backup-и: data\backups.
- При schema-upgrade спочатку створюється pre_migration backup сирого старого JSON.
- Імпорт приймає schema 18, 19 та 20 і приводить копію до schema 20.
- Перед імпортом створюється backup поточної бази.
- Export має ім'я combatlog_3.0_backup.json.

БЕЗПЕКА
-------
Збережено localhost-only listener, точний Host/Origin, Sec-Fetch-Site, JSON-only unsafe POST та випадковий per-process CSRF-токен. /healthz не повертає операційних даних.

WINDOWS TRUST
-------------
Portable містить VERIFY.cmd та INSTALL_CERT.cmd. Приватний ключ у комплект не входить. INSTALL_CERT.cmd може створити локальний non-exportable сертифікат у CurrentUser та підписати CombatLog.exe на конкретному ПК.
