# CombatLog changelog

## MAX 3.0 — stable schema 20

- Promoted the 2.9.3–2.9.5 TEST architecture to the normal production runtime: `127.0.0.1:18765`, `data/combatlog.json`, no TEST database/port.
- Added schema 20. Startup upgrade from schema 18/19 first writes a raw `pre_migration_schema...json` safety copy before changing the working database.
- NRK mission start is now a universal `Звідки` point, not a mandatory `ВП НРК`: any named CombatLog position or an arbitrary free-text place is valid.
- Mission route points use the same position-or-custom model. Named positions are canonicalized and rendered uppercase; arbitrary places preserve the operator's exact casing (`позиції, що облаштовується`, `район завантаження`, etc.).
- Existing schema-18/19 mission start snapshots migrate from legacy `PositionID/Position` into `Origin`; the legacy fields are cleared in schema 20.
- Stock NRK mission templates use `{{ originText }}` instead of hardcoding `ВП НРК «{{ position }}»`; old stock template fragments are upgraded automatically.
- Retains the data-driven UAV asset/field/certificate model, guided flight editor, unified module UI, unique-flight event statistics, active-mission panel, NRK lifecycle and auto/group mission shells from the TEST branch.


## MAX 2.9.5 TEST — guided flight entry and event counters

- `Події` now counts distinct flights, not UAV episode rows, while the chronological event count remains event-based.
- Manual flight entry suggests next sortie number and the latest crew/pilot/asset for the selected position without locking any value.
- Parsed and manual drafts use one guided editor with explicit action/result/detail blocks and a pre-save completeness check.
- Episode/add-ammo/add-damage actions are promoted to visible workflow buttons and the editor layout uses the available width responsively.

## MAX 2.9.4 TEST — isolated schema-19 refactor

- TEST runtime isolated on port 18766 with `data-test/combatlog-test.json` and separate backups; stable 2.9.2 can run in parallel.
- One-way import gate: schema 18 -> schema 19; future/older unsupported schemas rejected.
- UAV configuration changed to one complete data-driven field catalog per asset with enabled + main/additional placement.
- UAV certificates reduced to exactly three data-defined types: Ураження, Втрата борту, Мінування. Each concrete asset owns its own templates.
- Removed runtime action-global template routing and special FPV-fiber/Matrice/Mavic/Vampire branches; legacy routing is read only during schema-18 migration.
- `Події` and `Місії` now use date/time filters, shared time presets and filtered statistics; `Події` shows current unfinished/follow-up missions.
- Global Templates manager is for mission/group/module templates; concrete UAV templates are managed from `БпЛА / засоби`.
- Removed visible `Довідка не потрібна` filler from journal rows.
- Added runtime hardcoding contract test and schema-19 migration tests.
- Unified `Вильоти`, `Місії` and `Події` row UX: compact collapsed row, details/actions inside expansion, collapse-all, and one collapsible statistics-panel behavior.
- Mission lifecycle status is now separate from mission outcome and equipment state; evacuation/destruction no longer masquerade as mission status.
- `Події` rows are expandable and open the authoritative source only from the expanded detail.
- Pilot/call-sign, crew/group, position and settlement values are normalized to uppercase on input and persisted uppercase; uppercase catalog behavior is declared in data.
- Added catalog-driven `АВТОМОБІЛЬ` and `ГРУПА` mission-type UI stubs for later modules without adding separate table mechanics.
- Removed remaining field-name special cases from extra-field self-learning; asset-model fields are explicitly managed per asset and are never learned into an unscoped global model list.

- Редактор засобів и шаблонов упрощён: модели управляются внутри засобу, автоматические шаблоны действий видны отдельно от исключений конкретного засобу.


- Виправлено семантику `Проміжний звіт → Скиди`: це сумарна категорія бомберів, тому рахується кількість усіх вильотів профілів з тегом `role.drop`, незалежно від виду дії у конкретному епізоді.
- `Скиди` більше не залежать від `action_strike`: мінування, доставка та інші задачі бомбера все одно залишаються вильотом бомбера.
- Логіка data-driven: майбутній засіб з тегом `role.drop` автоматично потрапляє в суму без додавання його ID у код.
- Додано compatibility-патч метрики, який виправляє вже наявний `report_intermediate` без перезапису операторського тексту шаблону.
- `schemaVersion = 18`.

- Головний журнал отримав компактну desktop-щільність, щоб при 100% масштабу браузера виглядати приблизно так само містко, як раніше при 90%.
- Виправлено layout «Довідники / словники»: ліва панель та права панель списку ізольовані й не накладаються одна на одну.
- Кольори журналу централізовано в одному довіднику — `Результати`. `Наслідки ураження / втрат` більше не мають власного незалежного кольору.

- Мінування та втрата борту не мають hard-coded кольорів: колір є тільки якщо він призначений відповідному запису в `Результати`.

## 2.7.2 field-cleanup (15.08.2026)
- Спрощено модель вводу без зміни номера версії.
- `Результат` як і раніше береться тільки з явного поля `Результат:`; `Ціль`, коментар, БК та інший текст не створюють додатковий результат.
- Повністю прибрано з актуального вводу/парсингу: `Мета`, `Ціль`, `Частота`, `Ініціатор`, `Патруль`, `Маршрут / напрямок`, `Кінець інтервалу`, окрему `Дату епізоду`, окремий `ПДП`, `Кількість сесій`, ручну `Категорію` ураження та `Не вносити у звіт`.
- `Підрозділ` підставляється з налаштувань і зберігається як історичний знімок; редагування старого вильоту не переписує його поточними налаштуваннями.
- Уся географія відпрацювання перенесена на рівень епізоду: координати, НП, до/від ЛБЗ, відстань, територія та смуга оборони. Ручна корекція гео збережена.
- `підконтрольна / непідконтрольна` більше не редагується окремо: значення визначається з `до / від ЛБЗ`.
- Координати епізодів стали унікальними в усій базі; порівняння нормалізує регістр і пробіли, дубль блокує збереження та показує існуючий виліт.
- Серійний номер борту доступний і зберігається тільки для епізоду з `Втрата борту`; причина втрати також залишається умовним полем. Окремі дата/час втрати не використовуються.
- Starlink KIT/ID/S/N залишаються тільки у профілі з можливістю Starlink; камера, котушка/довжина та пройдена відстань залишаються умовними полями відповідних профілів.
- `Вид` більше не є ручним полем; він визначається профілем засобу. Модель БпЛА має одну користувацьку назву поля.
- БК показується лише для засобу/дії, що його використовує; `не розрив` та `аварійний скид` лишаються статусами БК.
- Блок `Ураження / втрати противника` лишається редагованим як актуальний результат; ручна категорія прибрана та визначається зі словника об’єктів.
- Пізніше уточнення ураження замінює актуальний стан без паралельного збереження старого `не уражено`.
- `Кількість вильотів` лишається лише для групової розвідки; кількість сесій мінування не зберігається і за потреби рахується з фактичного БК.
- Звіти/фільтрація смуги оборони використовують фактичну смугу епізоду; старе поле смуги вильоту під час нормалізації переноситься в епізоди та очищається.
## 2.7.2 deep-clean (15.08.2026)
- Проведено повну ревізію системи полів профілю після `field-cleanup`, без підвищення номера версії.
- Повністю прибрано старий механізм `fieldSets / hiddenFields` та секцію «успадкованих полів»: профіль має один явний список додаткових полів.
- `Камера` має один canonical ID `camera`; `Модель БпЛА` — один canonical ID `drone`. Старі `droneRadio / droneOpto` автоматично мігрують у `drone` і більше не показуються в інтерфейсі.
- Radio/opto більше не кодуються різними полями: профіль `FPV · радіо` прив’язує `drone` до `dronesRadio`, а `FPV · оптоволокно` — до `dronesOpto`.
- Редактор профілю показує тільки сумісні додаткові поля: FPV-radio — `Камера` + `Модель БпЛА`; FPV-opto — ці ж поля + котушка/довжина/пройдена відстань; Starlink-поля — тільки профілю з тегом Starlink.
- Сумісність додаткових полів стала data-driven через `refs.fields.requiresTag/profileConfigurable`; backend повторно очищає несумісні/дубльовані поля навіть при запиті зі старого UI.
- Прибрано невикористовувані profile metadata `class` та `hiddenFields`; старі backup-и читаються без повернення цих полів у робочу БД.
- Старе `flight.sector` тепер лише міграційне джерело: значення переноситься в порожні `episode.sector`, після чого дубль на рівні вильоту очищається.
- Додано regression/contract тести на відсутність дублів полів, коректну міграцію старих моделей FPV та гео, чистоту профілів і каталогу результатів.
## 2.7.2 flat-profiles (16.08.2026)
- Повністю видалено концепцію батьківських/дочірніх профілів і «полів-ознак». У профілю засобу більше немає `parentId`, `abstract`, `recognitionRules`, пріоритетів або окремого modal-вибору ознак.
- Редактор засобу має одну просту модель: основні поля застосунку є спільними для всіх засобів, а в секції «Додаткові поля» оператор вмикає тільки потрібні поля конкретного засобу.

- Стара metadata дочірніх профілів видаляється під час нормалізації/міграції і не може знову потрапити в збережений JSON.
- Для дистанційного мінування додано окрему довідку на один виліт: один виліт може містити кілька сесій/координат; кількість сесій не зберігається окремо, а рахується з фактичної кількості БК.
- Групова довідка мінування для 2+ вильотів збережена окремим шаблоном.
## 2.7.2 nrk-autobackup-ui (16.08.2026)
- Виправлено доступність дії `розвідка`: для штатних бомберів (`VAMPIRE`, `VAMPIRE · Starlink`, `NEMESIS`, `HEAVY SHOT`) compatibility-міграція вмикає `action_recon`, не змінюючи інші операторські налаштування можливостей. Форма нового/ручного епізоду синхронізує доступні дії з профілем засобу.
- `НРК` введено як повноцінний data-driven клас/засіб: додано `reportClass = НРК`, звичайний редагований профіль `НРК`, словникові aliases та підключення до звітів/конструкторів. Старий текст `НРК : 0` у проміжному звіті замінено реальним підрахунком.
- Додано автоматичний backup перед завершенням CombatLog: і для кнопки «Завершити CombatLog», і при автоматичному завершенні процесу після закриття останньої вкладки. Перезавантаження сторінки backup не створює.
- JSON backup переведено на canonical-структуру актуальної моделі: перед записом прибираються видалені/обчислювані дублікати (`endTime`, старі `purpose/target`, окрема дата епізоду, дубль `territory`, службова історія seed-міграцій). Import проходить через поточну нормалізацію і не повертає ці поля у робочу модель.
- Над журналом додано компактну кнопку `⇈` для згортання всіх розгорнутих рядків одним натисканням.
